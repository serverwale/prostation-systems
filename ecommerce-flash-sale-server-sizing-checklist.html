E-Commerce Server Sizing for Flash Sales: A Pre-Sale Checklist

An online store rarely fails on an ordinary day. It fails in the hour a sale goes live, when the extra traffic lands on the parts of the stack that are slowest to scale. This is a short checklist for stores that run on their own server; the full guide is ProStation's server sizing guide for high-traffic e-commerce and flash sales. Fully hosted platforms such as Shopify or BigCommerce scale on the platform's infrastructure, so this applies to self-hosted Magento, WooCommerce or a custom storefront.

Where a store breaks first

LayerWhy it fails at peakWhat to size generously
Database writesBrowsing is mostly cached reads; checkout is writes to orders, inventory and payment status that compete for the same rowsMemory so the working set stays cached, plus write-capable storage
Sessions and connectionsEvery cart and checkout in progress holds a database connection and some RAMRAM and connection limits for the concurrent peak, not the daily average
Disk I/OMany small writes queue up on slow storage before the CPU looks busyNVMe storage for consistent write throughput
CPUSimultaneous checkout requests need parallel processingMore cores, not only a faster single core
PowerA supply failure during the sale hour is the worst moment for itRedundant power supplies; see the redundant PSU guide

Checklist before the sale

  1. Know your peak. Estimate concurrent checkouts, not daily visitors, from your last sale or campaign.
  2. Load-test a week or two ahead. Simulate the expected peak against a staging copy so the limit is found on a quiet day, not during the sale.
  3. Protect order data. Fast is not enough; choose a RAID level that survives a drive failure (see RAID levels explained) and keep separate backups.
  4. Check storage type. Compare the options in the NVMe, SAS and SATA guide.
  5. Keep staging separate from production. See the dev, staging and production server guide.
  6. Decide where it runs. Compare your own server with colocation and cloud in the on-premise vs colocation vs cloud guide.
  7. Count the cost of downtime. A sale-hour outage costs more than the hardware gap; see the cost of server downtime and the warranty terms.

Frequently asked questions

  • Why does my store crash during a sale but not on a normal day? — Sale traffic concentrates on the hardest parts of the stack to scale: database writes for orders and inventory, active sessions and connections, and disk writes. A server sized for average traffic runs out of these first.
  • What should I size a store server for? — Size for peak concurrent checkout load, not average daily traffic. Give extra room to database memory, connection and session capacity, write storage and CPU cores.
  • Does this apply to Shopify? — No. Fully hosted platforms such as Shopify and BigCommerce run on the platform's own infrastructure, so scaling is the platform's job. This checklist is for self-hosted stores.
  • When should I load-test? — A week or two before a planned sale, against a staging copy, so any limit is found when nothing real is at stake.
  • Should the production server be new or refurbished? — A new build with a warranty suits the live customer-facing server. A refurbished server is a reasonable budget choice for a staging environment used only to rehearse the sale.
